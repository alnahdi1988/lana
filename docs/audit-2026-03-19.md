**Fixed SQL:**
```sql

       MAX(b.bar_timestamp) AS latest_bar_at,
       EXTRACT(EPOCH FROM (NOW() - MAX(b.bar_timestamp))) / 3600 AS age_hours,
       COUNT(*) FILTER (WHERE b.bar_timestamp > NOW() - INTERVAL '1 day') AS bars_last_24h
FROM bars b
JOIN symbols s ON s.id = b.symbol_id
WHERE b.timeframe = '15M'
GROUP BY s.ticker
ORDER BY latest_bar_at DESC
LIMIT 20;
```

## 6. Improvement Recommendations

### Top 3 Issues Blocking A/A+ Signal Delivery

**Issue 1 — Confidence ceiling on BULLISH_RECLAIM path is below A threshold**  
The scoring model maxes out at ~0.78 when signals fire on BULLISH_RECLAIM (the only active MTF state). A grade requires 0.80. Signals will never reach A unless the MTF state advances to `RECONTAINMENT_CANDIDATE` or the LTF trigger advances to `TRAP_REVERSE_BULLISH` or `FAKE_BREAKDOWN_REVERSAL`. The scoring weights need review: BULLISH_RECLAIM with perfect supporting conditions should be able to reach at least 0.80 if the system architecture considers that grade-worthy.

**Issue 2 — Micro confirmation is always `AVAILABLE_NOT_USED`**  
Micro (5M) data is being consumed and produces `LTF_BULLISH_RECLAIM` trigger states, but `require_micro_confirmation = False`. If micro confirmation were used, it would allow the signal engine to award the micro confirmation bonus. More importantly, using micro for confirmation as a quality gate could filter to only the highest-conviction setups that might also have better LTF triggers.

**Issue 3 — All 59 signals are from BULLISH_RECLAIM MTF state only**  
No signal has ever come from `RECONTAINMENT_CANDIDATE`, `DISCOUNT_RESPONSE`, or `EQUILIBRIUM_HOLD`. This indicates either: (a) the market universe never produces these states, or (b) the MTF evaluation is bottlenecked on BULLISH_RECLAIM. These higher-conviction states carry higher confidence scores and are the primary path to A/A+ grades.

### Top 3 System Reliability Gaps

**Gap 1 — Engine run_once process is stuck (PID 36180, no finished_at)**  
The engine cannot start new cycles because a zombie run_once process is registered as RUNNING. The launcher itself is dead (`launcher_running: false`). The runtime verifier confirms this as a FAIL blocker. Action: kill PID 36180 if alive, restart the launcher.

**Gap 2 — Engine loop is stopped (last heartbeat 3 days ago)**  
The engine loop process is in STOPPED state. The system is only running one-off cycles, not a continuous 15-minute loop. If the current run_once trigger is cron-based but the launcher is dead, there may be no automated engine execution happening.

**Gap 3 — `openclaw-ops-reconciler` skill is missing from disk**  
The TOOLS.md lists this skill as the canonical way to audit cron drift and job coverage. The skill file does not exist. There is no automated way to validate cron job coverage, detect drift, or reconcile scheduled vs actual executions.
